# SAR/GAMMA 影像处理知识与流程指导助手使用手册

## 0. 当前实际状态

本项目最初按 Phase 1 静态前端启动，但现在已经在本地增加了真实 RAG 对话原型：

```text
前端 React/Vite：http://127.0.0.1:5173/
后端 FastAPI：http://127.0.0.1:8000/
Embedding：SiliconFlow / BAAI/bge-m3
对话模型：DeepSeek / deepseek-chat
知识库：GAMMA 中文手册 + version2.0.2 处理代码
问答链路：规则路由 -> 可选 LLM 查询规划 -> 双库 RAG 检索 -> 必要时网页搜索 -> DeepSeek 证据化回答
```

当前程序仍然只做知识问答和流程指导，不执行 GAMMA，不执行 Shell，不使用 SSH，不连接 MCP Server，也不会修改、删除或覆盖你的数据处理文件。

密钥不要写入源码。当前后端启动时通过临时环境变量读取 `SILICONFLOW_API_KEY` 和 `DEEPSEEK_API_KEY`，前端 `.env.local` 只保存本地 RAG 接口地址。

当你问“怎么进行数据处理”“预处理代码怎么用”这类问题时，助手会优先回答 `version2.0.2` 中封装好的脚本或函数如何使用，只解释输入、输出、适用场景和最小占位符示例；不会默认展开脚本内部完整 GAMMA 流程。

处理代码解析结果可以直接检查这两个文件：

```text
knowledge/code/processing/processing_code_v2_0_2.chunks.jsonl
knowledge/code/processing/processing_code_v2_0_2.parsed_text.txt
```

其中 `parsed_text.txt` 是更适合人工阅读的纯文本解析结果。

## 1. 项目定位

本项目是面向学生的 SAR/GAMMA 影像处理知识与流程指导助手。当前已经实现本地前端、FastAPI 后端、GAMMA 手册库、处理代码库、向量检索和 DeepSeek 回答生成。

当前前端推荐使用 `rag_api` 模式。也就是说，浏览器只请求本地后端，DeepSeek 和 SiliconFlow 的密钥由后端通过临时环境变量读取，不写入前端代码。

当前版本不会执行任何真实处理任务：

1. 不执行 GAMMA。
2. 不执行 Shell 命令。
3. 不使用 SSH。
4. 不连接 MCP Server。
5. 不修改、删除或覆盖用户数据文件。
6. 不提供任务进度、暂停、恢复或执行日志。
7. 不在没有手册证据时生成真实精确参数顺序。

如果切回 `mock` 模式，页面中出现的手册名称、页码、命令和片段仍然只是 Phase 1 演示数据，不可替代真实 GAMMA 手册核验。

如果使用当前的 `rag_api` 模式，右侧来源来自本地 RAG 后端检索到的手册片段、处理代码片段，以及必要时触发的网页搜索摘要。

## 3. 真实 LLM 接入配置

项目根目录提供了 `.env.example`，里面所有真实连接信息都留给你填写。不要把真实密钥写进源码文件。

推荐做法是复制一份本地配置：

```bash
copy .env.example .env.local
```

然后编辑 `.env.local`：

```text
VITE_ASSISTANT_PROVIDER=llm_api
VITE_LLM_API_BASE_URL=
VITE_LLM_API_PATH=/v1/chat/completions
VITE_LLM_MODEL=
VITE_LLM_API_KEY=
VITE_LLM_TEMPERATURE=0.2
```

字段说明：

| 字段 | 是否必填 | 作用 |
|---|---|---|
| `VITE_ASSISTANT_PROVIDER` | 是 | 使用 `llm_api` 表示连接真实 LLM；使用 `mock` 表示回到本地模拟数据。 |
| `VITE_LLM_API_BASE_URL` | 使用 `llm_api` 时必填 | LLM 服务基础地址，例如由你自己的网关、本地代理或云服务提供。 |
| `VITE_LLM_API_PATH` | 是 | Chat Completions 路径，默认是 `/v1/chat/completions`。 |
| `VITE_LLM_MODEL` | 使用 `llm_api` 时必填 | 模型名称，由你使用的 LLM 服务决定。 |
| `VITE_LLM_API_KEY` | 视接口而定 | 如果接口需要 Bearer Token，就填写；如果本地后端代理负责注入密钥，可以留空。 |
| `VITE_LLM_TEMPERATURE` | 否 | 生成温度，默认 `0.2`。 |

重要安全提醒：

1. 这是前端项目，任何 `VITE_` 变量都会被打包进浏览器代码。
2. 如果你填写真实 API Key，浏览器端可以看到它，只适合本地学习或临时测试。
3. 更安全的正式方案是使用当前的 `rag_api` 路线：密钥只放在 FastAPI 后端环境变量里，前端只请求本地后端接口。
4. 当前项目只调用 LLM 文本接口，不执行 GAMMA、不执行 Shell、不使用 SSH。

## 4. GAMMA 手册向量化

当前项目已经可以把解析、切块后的 GAMMA 手册内容转换为向量索引。注意：这是开发阶段的知识库预处理脚本，不是前端助手在浏览器里执行 GAMMA 或 Shell 任务。

当前使用的输入文件：

```text
knowledge/gamma/chunks/gamma_new_user_manual_cn_2019.chunks.jsonl
```

生成的输出文件：

```text
knowledge/gamma/index/gamma_new_user_manual_cn_2019.embeddings.npy
knowledge/gamma/index/gamma_new_user_manual_cn_2019.embedding_records.jsonl
knowledge/gamma/index/gamma_new_user_manual_cn_2019.embedding_manifest.json
```

三个输出文件的作用如下：

| 文件 | 作用 |
|---|---|
| `*.embeddings.npy` | 真正的向量矩阵，每一行对应一个 chunk。 |
| `*.embedding_records.jsonl` | 向量行号和 chunk 元数据的对应关系，例如 `chunk_id`、`section_id`、`command_name`、页码等。 |
| `*.embedding_manifest.json` | 本次向量化的说明文件，记录模型、维度、数量、backend、生成时间和输出路径。 |

如果使用 SiliconFlow API，密钥不要写进源码，也不要写成 `VITE_` 前端变量。推荐只作为本地环境变量或后端环境变量使用：

```text
SILICONFLOW_API_BASE_URL=https://api.siliconflow.cn/v1
SILICONFLOW_EMBEDDING_MODEL=BAAI/bge-m3
SILICONFLOW_API_KEY=你的 SiliconFlow API Key
```

本次使用的向量化命令形式如下：

```powershell
$env:SILICONFLOW_API_KEY="你的 SiliconFlow API Key"
python .\scripts\embed_gamma_chunks.py --backend siliconflow --model BAAI/bge-m3 --batch-size 16 --api-max-chars 8000 --skip-demo
Remove-Item Env:\SILICONFLOW_API_KEY
```

当前生成结果：

| 字段 | 当前值 |
|---|---|
| backend | `siliconflow` |
| model | `BAAI/bge-m3` |
| embedding_count | `1926` |
| embedding_dimension | `1024` |
| dtype | `float32` |
| api_truncated_text_count | `0` |

查询这个索引时，用户问题也必须用同一个 embedding 模型转换为 query vector，否则向量空间不一致，检索分数没有意义。示例：

```powershell
$env:SILICONFLOW_API_KEY="你的 SiliconFlow API Key"
python .\scripts\search_gamma_index.py "SLC_intf 生成干涉图" --top-k 5
Remove-Item Env:\SILICONFLOW_API_KEY
```

`search_gamma_index.py` 当前采用“向量相似度 + 技术关键词加权”的混合检索。原因是 GAMMA 手册里有大量 `SLC_intf`、`SLC_mosaic_S1_TOPS` 这类精确命令名，纯语义向量检索容易把相似主题排在前面，但漏掉用户明确写出的命令名。

### 4.1 接入真实 RAG 对话

当前项目已经新增最小 FastAPI RAG 后端，链路如下：

```text
前端问题
→ FastAPI /api/chat
→ 规则路由判断问题类型和默认回答模式
→ 必要时调用 DeepSeek 生成 JSON 检索计划
→ SiliconFlow BAAI/bge-m3 生成 query embedding
→ 检索本地 GAMMA 手册向量库
→ 检索本地处理代码向量库
→ 本地证据不足或用户明确要求时，执行受控网页搜索
→ 构造带查询规划和引用证据的 RAG Prompt
→ DeepSeek Chat API 生成回答
→ 返回回答和 citation 列表给前端
```

两个知识库的分工：

| 知识库 | 作用 | 权威性 |
|---|---|---|
| GAMMA 手册库 | 确认命令、参数、输入输出、页码和章节 | 最高 |
| 处理代码库 | 说明项目脚本如何组织流程、如何封装命令、模板如何写 | 辅助 |
| 网页搜索 | 补充通用 SAR/InSAR 背景或本地证据不足的问题 | 外部参考 |

也就是说，代码里出现的命令用法不能反过来证明 GAMMA 官方语法；网页搜索也不能替代 GAMMA 手册。涉及精确参数顺序时，仍然必须以手册证据为准。

前端本地配置文件 `.env.local` 使用：

```text
VITE_ASSISTANT_PROVIDER=rag_api
VITE_RAG_API_URL=http://127.0.0.1:8000/api/chat
```

后端密钥只放在后端环境变量中，不要写进前端的 `VITE_` 变量：

```powershell
$env:SILICONFLOW_API_KEY="你的 SiliconFlow API Key"
$env:DEEPSEEK_API_KEY="你的 DeepSeek API Key"
$env:DEEPSEEK_CHAT_MODEL="deepseek-chat"
$env:WEB_SEARCH_ENABLED="true"
$env:WEB_SEARCH_PROVIDER="duckduckgo_lite"
$env:WEB_SEARCH_MAX_RESULTS="3"
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

健康检查接口：

```text
http://127.0.0.1:8000/api/health
```

前端地址：

```text
http://127.0.0.1:5173/
```

## 6. 页面布局说明

界面采用简化 Codex 风格三栏布局。

左侧栏：

1. 显示产品名称。
2. 提供“新建会话”按钮。
3. 展示历史会话。
4. 支持切换会话。
5. 支持删除会话。

中间栏：

1. 显示当前会话标题。
2. 展示 Agent 流程标签，例如 `assistant_engine: llm_api`、`llm_config: missing/ready`、`classify_query`、`retrieve_documents`、`validate_grounding`。
3. 提供快捷问题按钮。
4. 显示学生提问和助手回答。
5. 使用 Markdown 渲染回答内容。
6. 对 `gamma` 和 `python` 等代码块显示代码类型。
7. 每个代码块都有复制按钮。
8. 助手回答可复制整段内容。
9. 输入框旁明确提示当前版本不会执行真实任务，LLM 接口仅预留且当前未启用。

右侧栏：

1. 显示当前回答关联的模拟文档来源。
2. 每条来源包含 `source`、`page`、`command_name`、`section`、`verification_status`、`retrieval_score` 和原始文本片段。
3. 如果回答证据不足，会显示 `insufficient_evidence` 类型来源。

## 7. 支持的问题类型

源码中定义了 6 类问题，位于 `src/types.ts`：

```ts
export type QueryType =
  | "concept"
  | "workflow"
  | "command"
  | "parameter"
  | "file_layout"
  | "code_template";
```

这些类型含义如下：

| 类型 | 含义 |
|---|---|
| `concept` | SAR、InSAR、SLC、相干性、相位等基础概念。 |
| `workflow` | 某个 SAR/InSAR 处理目标的完整流程。 |
| `command` | 某个处理步骤可能使用的 GAMMA 命令。 |
| `parameter` | 命令参数的名称、类型、作用、必填关系和输入输出关系。 |
| `file_layout` | 原始数据、DEM、SLC、参数文件、干涉图和结果文件的推荐目录。 |
| `code_template` | 使用占位符生成命令行或 Python 代码模板。 |

一个问题可以匹配多个类型。例如“从两景 SLC 生成干涉图的流程是什么？”会同时匹配 `workflow`、`command` 和 `file_layout`。

## 8. 核心源码讲解

### 8.1 `src/main.tsx`

这个文件只做一件事：把 React 应用挂载到 `index.html` 中的 `<div id="root"></div>`。

核心代码：

```tsx
ReactDOM.createRoot(document.getElementById("root") as HTMLElement).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>,
);
```

你可以把它理解为“打开应用的电源开关”。真正的界面逻辑都在 `App.tsx`。

### 8.2 `src/types.ts`

这个文件定义数据结构，让 TypeScript 知道每类数据长什么样。

重要类型：

| 类型 | 说明 |
|---|---|
| `QueryType` | 问题类型。 |
| `VerificationStatus` | 引用验证状态。 |
| `Citation` | 右侧文档来源卡片的数据结构。 |
| `ChatMessage` | 单条聊天消息。 |
| `ChatSession` | 一个完整会话。 |
| `MockAnswer` | 一条模拟回答模板。 |

其中 `Citation` 对应右侧栏：

```ts
export interface Citation {
  id: string;
  source: string;
  page: string;
  command_name: string;
  section: string;
  verification_status: VerificationStatus;
  retrieval_score: number;
  excerpt: string;
}
```

这正好覆盖需求中的来源字段。

### 8.3 `src/data/mockKnowledge.ts`

这个文件是 Phase 1 的静态“知识库”。它不读取真实 PDF，不做向量检索，不调用模型，只根据关键词匹配预设答案。

主要内容：

| 变量或函数 | 作用 |
|---|---|
| `quickQuestions` | 中间栏顶部的快捷问题按钮。 |
| `queryTypeLabels` | 问题类型标签显示文本。 |
| `verificationLabels` | 引用验证状态显示文本。 |
| `mockAnswers` | 预置模拟回答。 |
| `insufficientEvidenceAnswer` | 证据不足时的兜底回答。 |
| `initialAssistantMessage` | 新会话的欢迎消息。 |
| `seedSessions` | 首次打开应用时的示例历史会话。 |
| `classifyQuestion()` | 根据关键词给问题打类型标签。 |
| `selectMockAnswer()` | 根据关键词选择最匹配的模拟回答。 |

例如 `classifyQuestion()` 会根据问题文本判断类型：

```ts
if (/流程|步骤|如何|怎么做|生成|workflow|处理目标/.test(normalized)) {
  types.add("workflow");
}
```

如果问题中包含“流程”“步骤”“如何”等词，就会加上 `workflow` 标签。

`selectMockAnswer()` 会统计问题命中了多少触发词：

```ts
const scored = mockAnswers
  .map((answer) => ({
    answer,
    score: answer.triggers.reduce(
      (total, trigger) => total + (normalized.includes(trigger.toLowerCase()) ? 1 : 0),
      0,
    ),
  }))
  .sort((left, right) => right.score - left.score);
```

如果没有命中任何触发词，就返回“证据不足”回答。这符合“不编造命令和参数”的产品要求。

### 8.4 `src/App.tsx`

这是最重要的文件，负责完整界面和交互。

主要状态：

```tsx
const [sessions, setSessions] = useState<ChatSession[]>(readStoredSessions);
const [activeSessionId, setActiveSessionId] = useState(...);
const [input, setInput] = useState("");
const [activeSourceMessageId, setActiveSourceMessageId] = useState<string | null>(null);
```

这些状态分别表示：

| 状态 | 含义 |
|---|---|
| `sessions` | 所有会话。 |
| `activeSessionId` | 当前选中的会话 ID。 |
| `input` | 输入框中的问题。 |
| `activeSourceMessageId` | 右侧正在展示哪条助手回答的引用。 |

会话会保存在浏览器 `localStorage` 中：

```tsx
useEffect(() => {
  window.localStorage.setItem(STORAGE_KEY, JSON.stringify(sessions));
}, [sessions]);
```

这只保存浏览器本地状态，不会写入你的项目文件，也不会覆盖用户数据。

发送问题的核心函数是 `sendQuestion()`。它不直接调用 mock 数据，而是调用统一服务层：

```tsx
const assistantResponse = await answerStudentQuestion({
  question,
  sessionId: activeSession.id,
  messages: activeSession.messages,
});
```

这样 UI 和回答来源解耦。当前 `answerStudentQuestion()` 会根据 `.env.local` 中的 `VITE_ASSISTANT_PROVIDER` 选择 mock provider 或真实 LLM provider。

新建会话由 `createSession()` 完成，删除会话由 `deleteSession()` 完成。

Markdown 渲染由 `MarkdownMessage` 组件完成，代码块复制由 `CodeBlock` 组件完成。

### 8.5 `src/services/assistantEngine.ts`

这个文件是助手回答服务层，也是连接 LLM 大模型的位置。界面不会直接接触 mock 数据或 fetch 细节，而是调用统一函数：

```ts
answerStudentQuestion(request)
```

它包含两个 provider：

```ts
mockAssistantProvider
llmApiAssistantProvider
```

当前实际启用哪个，由 `.env.local` 决定。现在推荐使用：

```ts
VITE_ASSISTANT_PROVIDER=rag_api
VITE_RAG_API_URL=http://127.0.0.1:8000/api/chat
```

如果设置为 `rag_api`，前端会把问题发给本地 FastAPI 后端，由后端负责手册检索、代码库检索、必要时网页搜索和 DeepSeek 调用。

如果设置为 `llm_api`，程序会绕过本地 RAG 后端，直接向 OpenAI-compatible Chat Completions 接口发送请求：

```ts
await fetch(`${llm.baseUrl}${llm.endpointPath}`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    ...(llm.apiKey ? { Authorization: `Bearer ${llm.apiKey}` } : {}),
  },
  body: JSON.stringify({
    model: llm.model,
    messages: toChatMessages(request.messages, request.question),
    temperature: llm.temperature,
  }),
});
```

如果配置缺失，程序不会假装已经连上模型，而是返回“LLM 尚未配置”的说明，并在右侧来源中列出缺少的字段。

注意：`llm_api` 模式没有本地 RAG 引用验证，模型回答不能自动视为手册证据。需要真实手册、代码和网页来源时，请使用 `rag_api`。

## 9. 问答如何工作

用户点击快捷问题或手动输入问题后，程序走下面的运行时流程：

```text
用户输入
  -> answerStudentQuestion(request)
  -> activeAssistantProvider
  -> 如果 VITE_ASSISTANT_PROVIDER=rag_api
       -> ragApiAssistantProvider
       -> fetch http://127.0.0.1:8000/api/chat
       -> backend/main.py classify_query
       -> backend/query_planner.py 规则路由
       -> 必要时 DeepSeek 生成 JSON 检索计划
       -> SiliconFlow 生成 query embedding
       -> rag_index.py 检索手册库和代码库
       -> 本地证据不足或用户明确要求时，web_search.py 执行网页搜索
       -> prompt_builder.py 构造受控 RAG prompt
       -> DeepSeek 基于证据生成回答
  -> 如果 VITE_ASSISTANT_PROVIDER=llm_api
       -> llmApiAssistantProvider
       -> 检查 .env.local 配置
       -> fetch LLM Chat Completions API
  -> 如果 VITE_ASSISTANT_PROVIDER=mock
       -> mockAssistantProvider
       -> classifyQuestion(question)
       -> selectMockAnswer(question)
  -> 生成用户消息
  -> 生成助手消息
  -> 展示 Markdown
  -> 右侧展示 citations
```

这对应需求中的 Agent 流程：

```text
START
→ classify_query
→ extract_context
→ check_missing_information
→ 可选 query_planner
→ retrieve_documents
→ 必要时 web_search
→ evaluate_evidence
→ 根据问题类型生成回答
→ validate_grounding
→ format_response
→ END
```

当前已经实现了本地双库检索、引用来源返回和封装脚本优先回答控制。还没有实现 LangGraph 状态机，也没有做完整自动评估；`validate_grounding` 目前主要依靠提示词约束、引用证据和封装回答违规重写来实现。

## 10. 如何新增一个模拟回答

打开：

```text
src/data/mockKnowledge.ts
```

在 `mockAnswers` 数组中新增一项：

```ts
{
  id: "answer-new-topic",
  title: "新主题",
  triggers: ["关键词1", "关键词2"],
  queryTypes: ["workflow", "command"],
  citations: [
    {
      id: "src-new-01",

      page: "p. 1",
```

3. `citations` 控制右侧来源面板。
4. `answer` 使用 Markdown，可以包含表格和代码块。

## 12. 如何理解右侧引用来源

右侧卡片来自 `Citation` 数据。每张卡片包含：

| 字段 | 含义 |
|---|---|
| `source` | 手册或资料名称。 |
| `page` | 页码。 |
| `command_name` | 命令名称，没有命令时为 `N/A`。 |
| `section` | 章节。 |
| `verification_status` | 验证状态。 |
| `retrieval_score` | 检索分数。 |
| `excerpt` | 原始片段。 |

当前常见状态值包括：

| 状态 | 含义 |
|---|---|
| `manual_verified` | 手册证据较明确。 |
| `partial_manual_evidence` | 有手册片段，但证据强度一般。 |
| `code_reference` | 来源是处理代码库片段。 |
| `web_reference` | 来源是网页搜索摘要，只能作为外部补充。 |
| `insufficient_evidence` | 证据不足。 |

如果切回 `mock` 模式，前端仍可能显示 Phase 1 的模拟状态；使用 `rag_api` 时，状态来自后端真实检索结果。

## 13. 为什么不会执行 GAMMA 任务

本项目没有实现任何执行入口。

后端虽然使用 FastAPI，但它只提供问答接口。源码中没有：

1. `child_process`。
2. `subprocess`。
3. SSH 客户端。
4. MCP 客户端。
5. 文件上传处理。
6. 真实 GAMMA 调用。

Python 模板中只生成列表并 `print()` 命令字符串，而且模板本身只是展示在页面中的文本，不会在浏览器中运行。

## 14. 后续阶段建议

最初规划的阶段如下。当前已经做出了 Phase 2、Phase 3 和 Phase 4 的本地原型，但还没有实现 LangGraph 受控流程和系统化评估。

| 阶段 | 建议新增内容 |
|---|---|
| Phase 2 | FastAPI 接口、会话模型、前后端通信。当前已有本地原型。 |

当前代码仍然遵守“不执行 GAMMA 真实任务”的边界。
